# TASK-001 — Ядро боя `ivcore` (C++17, без Unreal)

**Ветка:** `claude/task-001-gameplay-core` → Pull Request в `main`.
**Источник правды:** `docs/pitch/02_pitch/IMPACT_VECTOR_FULL_PITCH_RU.md` (номера разделов ниже — оттуда).
**Область:** только `core/`, `docs/CORE_API.md`, `docs/BALANCE_REPORT.md`, `.github/workflows/core.yml`. Остальное не менять.

## Цель
Написать и проверить тестами детерминированное ядро боевой системы IMPACT VECTOR, которое я (локальный Claude) затем
подключу в Unreal Engine 5. Ядро — чистая симуляция: данные на входе (намерения игрока/ИИ), данные на выходе
(состояние тел, события). Никакой графики, звука, физики мира.

## Технические требования
- C++17, CMake ≥ 3.20, сборка `g++`/`clang++` с `-Wall -Wextra -Werror`. Только стандартная библиотека.
- Без исключений, без RTTI, без глобального изменяемого состояния. Публичные типы — простые структуры (POD где возможно),
  чтобы их легко обернуть в `USTRUCT`.
- Фиксированный шаг `kTickHz = 60`. Время в тиках (целые). Миллисекунды из питча переводить в тики в `Tuning.h`.
- Свой ГПСЧ (PCG32 или xoshiro) с сидом. Один и тот же сид + одни и те же входы = побитово одинаковая история событий (тест на это обязателен).
- Тесты — без внешних зависимостей (свой мини-макрос `IV_TEST`/`IV_CHECK` в `core/tests/TestFramework.h`), запуск через `ctest`.
- Все константы баланса — только в `core/include/iv/Tuning.h`, у каждой комментарий `// pitch §N`.

## Модули (по порядку; каждый со своими тестами)

### 1. `Body` и зоны (§9, §14)
9 зон: `Head`(сенсоры), `Torso`(центр/грудь), `Reactor`(задняя часть корпуса), `ShoulderL/R`, `ArmL/R`(локоть+кисть), `LegL/R`.
Три слоя прочности на зону: `Armor` → `Mechanism` → `System`. Урон сначала съедает броню, затем механизм, затем систему.
Состояния зоны: `Intact, Dented, Exposed, Damaged, Critical, Destroyed`. `ArmL/R` и `LegL/R` можно перейти в `Severed`
(только после `Destroyed` сустава и при условии удара/захвата, §9 «Плечи и руки», §12).
Функциональные эффекты (выдавать как структуру `Modifiers`, пересчитываемую при каждом изменении):
скорость замаха, дальность, возможность менять траекторию, сила блока, скорость шага, поворот, доступность уклонения,
устойчивость/восстановление, возможность захвата (кисть), возможность тарана (ноги), задержка захвата цели и «слепые сектора»
(голова), точность орудия. Каждый эффект — монотонная функция состояния зоны, формулы в `Tuning.h`.
Условия конца боя (§14 «Победа без обычной полоски»): реактор разрушен / кабина критична / полная потеря подвижности /
отключение питания / обе руки потеряны + обездвижен. Возвращать причину (`enum EndReason`).

### 2. Ресурсы (§10)
`Stability` (падает от блока, попаданий, промахов, резких разворотов; ноль → `Staggered`/`Knockdown`), `Heat` (заряженные
удары, финты, аварийное торможение, повреждённые приводы; высокий нагрев → штрафы, течь охлаждения, риск отключения),
`Energy` с приоритетом `Arms/Legs/Guard/Weapon` и **задержкой переключения** (видимый противнику «поток энергии» — событие).

### 3. Combat Vector — формирование удара (§5)
Намерение: `{ SwingSide{Up,Left,Right,Down}, TargetZone, Footwork{StepIn,Hold,Turn,StepBack}, Arm{L,R} }`.
Фазы: `Idle → Windup → (CommitPoint) → Strike → Contact → Recovery`. Отмена `B` до точки фиксации — бесплатна/дёшева;
после — «аварийное торможение» (потеря стабильности + нагрев). Быстрые удары (§5.3) — отдельный короткий путь, перебивают
долгий замах. Финты (§8): смена цели/руки/превращение в захват до фиксации, каждый финт копит тепло и замедляет.
Ограниченные ветки одного замаха (§8 «Ограниченные ветки»): таблица допустимых продолжений для каждого `SwingSide`.
**Экономика позы (§5.4):** после удара рука остаётся в позе (`ArmPose`), от неё зависят доступные следующие удары и время
возврата. Реализовать как конечный автомат поз + таблицу допустимых переходов.
Вклад ног: `Footwork` и опора (`FootPlant`) меняют силу, скорость восстановления и расход стабильности (§5.2 п.3, §11, §19 «One Frame»).

### 4. Защита и контратаки (§6, §7)
Блок (по сектору, снижает урон, но тратит стабильность и нагружает руку), усиленная стойка (энергия, неподвижность, уязвимость
ног и захвата), парирование (окна из §6: блок 350–450 мс, парирование 140–200 мс, перехват 90–140 мс, ответ на контратаку 70–110 мс —
как стартовые значения в `Tuning.h`), уклонение (один тяжёлый шаг + время стабилизации, уязвимость к широким ударам/захватам).
Перехват и свойство «внутренняя линия»: запоздалый обычный блок против успешной контратаки не срабатывает.
Цепочка реверсов: максимум 2 ответа, каждый следующий — меньше окно, больше расход энергии, больше штраф за ошибку; затем
физический клинч (§7). Исход клинча зависит от стабильности, угла корпуса, опоры ног, повреждений рук, направления движения
и близости стены (передавать `proximityToObstacle` как входной параметр).

### 5. ИИ противника (§20)
ИИ видит **только то же, что человек**: позу, фазу противника, видимый сектор замаха, звуковой сигнал зарядки, направление
энергии, дистанцию, повреждения. **Не читает намерения игрока напрямую** (тест, который это доказывает: ИИ получает только
структуру `Observation`). Архетипы: `Counterpuncher, Breaker, LimbHunter, Trickster, Gunner, Grappler`.
Сложность меняет задержку реакции (в тиках, не меньше ~12 тиков ≈ 200 мс на любом уровне), глубину анализа привычек,
качество выбора позиции — **не** урон. Память привычек (§8 «Поведенческое чтение»): счётчики «после блока отходит вправо» и т. п.

### 6. Headless-симулятор и баланс
`ivsim`: консольная программа, гоняет N дуэлей ИИ-против-ИИ (все пары архетипов × 3 сложности × разные сиды), пишет CSV
событий и сводку. В `docs/BALANCE_REPORT.md` — реальные числа из запуска: средняя длительность боя (цель 8–12 минут игрового
времени — если не попадаем, подкрутить `Tuning.h` и описать что менялось), доля побед по архетипам (ни один не должен
выигрывать > 65% у остальных), распределение причин конца боя, частота отрыва рук, средняя доля ударов в каждую зону,
доля парирований/перехватов от всех защит.

## Приёмка (Definition of Done)
1. `cmake -S core -B build && cmake --build build && ctest --test-dir build --output-on-failure` проходит с нуля.
2. Тест детерминизма (двойной прогон с одинаковым сидом, сравнение хэша истории событий) зелёный.
3. Тесты на каждый модуль, минимум по 8 осмысленных проверок на модуль, включая граничные случаи (отмена ровно на точке
   фиксации, третий реверс → клинч, отрыв руки только после `Destroyed`, ИИ не может реагировать быстрее минимума).
4. `docs/CORE_API.md` — как подключить ядро (какие структуры подаются на вход, какие события выходят, пример игрового цикла на 20 строк).
5. `docs/BALANCE_REPORT.md` с реальными цифрами; GitHub Actions workflow собирает и гоняет тесты на ubuntu-latest.
6. В описании PR: что сделано, **какие команды реально запускались и их результат**, что не проверено, известные ограничения.
